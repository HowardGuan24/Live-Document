# V9 机制驱动三角洲解释动画：生成、验证与复现报告

当前状态：`AWAITING_HUMAN_BLIND_TEST`

这份报告是一份可以独立阅读的说明书。读者不需要看过 V1–V8，也不需要了解视频
生成模型或 Python。本文会回答四个最基本的问题：

1. 这个动画想解释什么？
2. 画面中的泥沙、沉积、新陆地和分流究竟是谁生成的？
3. 从参数到 GIF/MP4，完整生成流程是什么？
4. 当前结果通过了哪些检查，还有什么没有得到证明？

---

## 1. 先看结果

建议第一次阅读时按以下顺序查看：

1. [正式 GIF](runs/v6-causal/v6_causal.gif)：最方便快速检查完整叙事。
2. [八个关键时刻的静态总览](runs/v6-causal/contact-sheet.jpg)：方便停下来比较变化。
3. [正式 MP4](runs/v6-causal/v6_causal.mp4)：适合播放器逐帧查看。
4. [人工盲测记录表](blindtest.md)：正式验收仍缺这一步。

画面要表达的因果链是：

> 河流携带悬浮泥沙 → 河水进入开阔水域后减速 → 泥沙沉降并在水下逐层堆积
> → 沉积厚度超过当地水深后露出水面 → 新生陆地阻挡水流，水流绕行并形成分支。

正式成片为 768×512、12 fps、105 张展示帧、8.75 秒。GIF 大小为 228,333
bytes，MP4 大小为 359,929 bytes。

这里的 “V6 causal” 不是项目版本倒退。V9 任务沿用了上轮 V1–V5 的实验编号，
因此本轮新增的因果机制方案在 V9 目录中被命名为 `v6-causal`。

## 2. 这个结果不是文生视频模型生成的

正式动画没有使用 LTX、Wan、Stable Video Diffusion 或其他生成式图像/视频模型。
它也没有让 AI “想象一个三角洲长什么样”。正式生成过程是：

* Python 数值规则负责计算水流、泥沙输运、沉积厚度和新生陆地；
* Python/Pillow 负责把这些数值画成箭头、颗粒、颜色和文字；
* FFmpeg、Pillow 和 gifsicle 负责把 PNG 帧编码为 MP4/GIF；
* 正式生成过程关闭了 CUDA 和 HIP，没有使用 GPU。

因此，画面中能够看到的细节分为两类：

### 2.1 机制数据决定的内容

* 水流箭头的方向和长度；
* 悬浮泥沙颗粒的位置；
* 水下沉积的范围和厚度；
* 哪些网格已经变成新生陆地；
* 水流何时开始绕开新陆地；
* 最后出现几条可测量的高速水流通道。

### 2.2 为了让人读懂而增加的视觉说明

* 中文阶段字幕；
* 固定图例；
* 原有陆地的斜线纹理；
* 字幕和图例背后的深色底板；
* 五个阶段进度点；
* 箭头头部的形状和线条样式。

第二类元素只负责“讲清楚”，不会改变第一类机制数据。换句话说，Python 绘图代码
可以决定一支箭画成什么颜色，但不能擅自把箭头转向，也不能手画一块三角洲陆地。

本地 Gemma 3 12B 只在成片完成后用于一次辅助坐标评测，并且严格运行在 CPU 上。
它没有参与模拟、绘图或视频生成。该评测失败，详情见第 12 节。

## 3. 完整生成流程总览

从输入到交付物，数据只沿一个方向流动：

```text
任务要求 prompt/v9.md
        │
        ├── 定义五段教学叙事 storyboard.json
        └── 定义模拟参数 SimulationConfig
                         │
                         ▼
              机制模拟 deposition_model.py
                         │
                         ▼
        120 个逐帧状态 states.jsonl（事实来源）
                         │
                 自动机制检查
         validate_mechanism.py + 单元测试
                         │
             通过后才允许正式绘图
                         ▼
                 渲染器 render.py
       从状态中选帧、加停留时间、画成 105 张 PNG
                         │
                         ▼
                  导出器 export.py
       ├── FFmpeg → MP4
       ├── FFmpeg + Pillow + gifsicle → GIF
       ├── 关键帧 → contact sheet
       └── 写出 timeline.json 和 metadata.json
                         │
                         ▼
             三位零基础参与者人工盲测
                 （目前尚未完成）
```

这个分层非常重要：

* `states.jsonl` 是“发生了什么”的记录；
* PNG 是“如何把这些事实画出来”；
* MP4/GIF 是“如何把 PNG 交付给人观看”；
* 人工盲测才回答“一个零基础的人是否真的看懂了”。

编码器不能回过头修改状态，渲染器也不能凭空发明状态里不存在的陆地或河道。

## 4. 第一步：先定义初始环境和参数

机制模拟在一个 96×64 的网格上进行。可以把它想象成一张由 6,144 个小方格组成的
地图。正式画面为 768×512，所以每个模拟格大致对应 8×8 个屏幕像素。

初始地图包含：

* 左侧的原有陆地；
* 从左侧流向右侧的窄河道；
* `x=38` 处的海岸线；
* 海岸线右侧的水域；
* 每个水域格子的水深。

水深并不完全相同：河口附近设置为相对较深的冲刷区，河口外有一片较浅的水下
区域。这个设计不是预先画好的三角洲轮廓，而是提供“沉积厚度超过水深时可以露出
水面”的地形条件。

正式使用的参数如下：

| 参数          |      正式值 | 用普通语言解释         |
| ----------- | -------: | --------------- |
| 网格          |    96×64 | 模拟地图的精细程度       |
| fps / 最大状态数 | 12 / 120 | 机制模拟记录 10 秒     |
| 随机种子        |     1909 | 保证相同参数能够复现同一结果  |
| 每帧新增泥沙颗粒    |       14 | 河流持续输入多少份悬浮泥沙   |
| 河道速度        |     1.34 | 泥沙在河道里的基础移动速度   |
| 入海扩张率       |     0.35 | 水流进入开阔水域后减速得多快  |
| 海域最低速度      |     0.16 | 避免远处水流完全静止      |
| 基础沉降率       |     0.02 | 低速泥沙每帧沉下去的概率尺度  |
| 单次沉积质量      |     0.12 | 一份落底泥沙增加多少厚度    |
| 沉积分散半径      |        2 | 一份泥沙分摊到周围 5×5 格 |
| 横向微扰        |    0.055 | 模拟颗粒不会走完全相同的直线  |
| 河口保护列数      |        2 | 泥沙越过河口两格后才允许沉降  |
| 稳定通道门槛      |      5 帧 | 分流至少持续 5 帧才算成立  |
| 流场采样间隔      |      4 格 | 每隔四格保存一支可视化箭头   |

配置由
[`deposition_model.py`](../../blackbox/v9_causal/deposition_model.py)
中的 `SimulationConfig` 管理，实际运行参数同时写入
[`simulation_config.json`](mechanism/simulation_config.json)，避免报告与真实运行不一致。

## 5. 第二步：每一帧的机制是怎样计算的

120 个机制状态不是一次性画出来的。程序从 frame 0 到 frame 119 循环，每一帧都
按以下顺序更新。

### 5.1 根据当前陆地重新计算水流

程序先把所有陆地格标记为“水不能通过”，水域格标记为“可以通过”。左边河流入口
是高势能边界，右边开阔水域边缘是低势能边界。程序反复求解一个简化的势场，再沿
势能下降方向得到水流方向。

可以用一个不严格但直观的比喻理解：假设地图是一张斜坡，水会沿着坡面从高处往
低处流；当中间出现一块新陆地时，这块地方变成墙，坡面会重新调整，水自然从墙的
两侧绕开。

代码没有预先写：

* “上面画一条支流”；
* “下面再画一条支流”；
* “最终必须长成两条河道”；
* “把陆地画成这个目标多边形”。

程序里没有 `target_channel_count`。最后的两条通道是模拟后测量到的结果，不是输入
给模拟器的目标。

对应实现：
[`flow_field()` 和 `reroute()`](../../blackbox/v9_causal/primitives.py)。

### 5.2 河水入海后减速

窄河道进入开阔水域后，流动横截面扩大。V9 用下面的简化关系表达减速：

```text
海中速度 = 河道速度 ÷ (1 + 扩张率 × 离岸距离)
```

速度不会低于设定的海域最低速度。箭头长度直接来自这个速度，因此观众看到河道中
的箭头较长，进入海域后的箭头逐渐变短。

泥沙第一次到达海岸的 frame 28，河口区域平均速度约为上游河道平均速度的
`0.36017`，即只有上游的约 36%。这是“入海减速”的数值证据。

对应实现：
[`decelerate()`](../../blackbox/v9_causal/primitives.py)。

### 5.3 注入并搬运悬浮泥沙

每帧在左侧河流入口新增 14 个泥沙颗粒。每个颗粒拥有：

* 唯一编号；
* 当前横坐标 `x`；
* 当前纵坐标 `y`；
* 已经运动了多少帧 `age`；
* `suspended`，即仍然悬浮的状态。

颗粒沿当前位置的水流速度向量移动，并加入很小的横向随机扰动。随机种子固定为
1909，因此这种扰动可复现，不会每运行一次得到一个完全不同的三角洲。

如果颗粒即将撞上新陆地，程序会读取相邻可通行格的流向，优先选择向下游前进的
路线。这仍然来自当前流场，不是绘图层给颗粒编排路径。

对应实现：
[`transport()`](../../blackbox/v9_causal/primitives.py)。

### 5.4 水流越慢，泥沙越容易沉降

颗粒必须越过海岸线后的两列保护区，才有资格沉降。这样可以避免所有泥沙刚到河口
就堆成一道墙。

满足位置条件后，每颗泥沙的沉降概率由减速程度决定：

```text
减速程度 = 1 - 当前速度 ÷ 河道速度
沉降概率 = 基础沉降率 × 减速程度²
```

因此：

* 流速接近河道速度时，沉降概率接近 0；
* 流速下降后，沉降概率明显提高；
* 被判定沉降的颗粒从悬浮列表移除，转为海床沉积。

第一次泥沙到岸是 frame 28，第一次真实沉降是 frame 32。沉降没有发生在泥沙抵达
之前，也不是根据字幕时间硬切出来的。

### 5.5 沉积不是色块，而是不断增加的厚度

每一份落底泥沙不会只填充一个孤立像素。它的质量通过一个归一化的 5×5 平滑核
分配到附近格子，形成较连续的沉积层。程序把累积结果保存在 `thick` 二维数组中。

这个数组只增不减，代表同一位置的海床沉积越来越厚。渲染时将它量化为六个赭色
层级，所以观众能够看到“水下沉积由薄变厚”，而不是突然出现一块固定色斑。

对应实现：
[`accumulate()`](../../blackbox/v9_causal/primitives.py)。

### 5.6 沉积厚度超过水深，才变成新生陆地

每一个格子都使用同一条阈值规则：

```text
当前陆地 = 原有陆地 OR（沉积厚度 > 当地水深）
```

在厚度尚未超过水深时，该格仍然是水下沉积；超过水深后才被标记为新生陆地。第一次
出水发生在 frame 101。这里不存在“到了第 101 帧就播放一张陆地图片”的逻辑，
frame 101 只是这次参数运行中第一次满足阈值的时刻。

对应实现：
[`threshold_change()`](../../blackbox/v9_causal/primitives.py)。

### 5.7 新生陆地反过来改变下一帧的水流

frame 101 出现的新陆地，在下一轮计算中成为不可通行障碍。势场重新求解后，水流
绕开它；颗粒也跟随新的水流路径移动，随后在新的低速区域继续沉降。

这构成一个闭环：

```text
水流搬运泥沙
   ↓
减速使泥沙沉降
   ↓
沉积达到水深阈值，形成新陆地
   ↓
新陆地改变水流
   ↓
改变后的水流继续搬运和沉积泥沙
```

程序在沉积前缘测量彼此分开的高速水域段。最终测得 2 条通道，并在最后 15 个机制
状态中持续稳定。这里的“2 条”是输出统计，不是生成条件。

## 6. 第三步：把每帧事实写入 `states.jsonl`

模拟不会直接生成视频。它先把每一帧完整保存成一行 JSON，得到
[`states.jsonl`](mechanism/states.jsonl)。该文件共有 120 行，一行对应一个机制
时刻。

下面是结构示意。为便于阅读，二维数组被省略；真实文件保存的是完整数据：

```json
{
  "frame": 101,
  "time_seconds": 8.4167,
  "beat_id": "threshold_change",
  "caption": "沙洲露出水面",
  "particles": [
    {"id": 123, "x": 42.1, "y": 31.8, "age": 35, "state": "suspended"}
  ],
  "thick": ["64×96 的完整沉积厚度数组"],
  "land": ["64×96 的完整陆地数组"],
  "new_land": ["64×96 的完整新生陆地数组"],
  "flow_samples": [
    ["x", "y", "横向速度", "纵向速度", "总速度"]
  ],
  "stats": {
    "settled_particles": "累计沉降颗粒数",
    "new_land_cells": "新生陆地格数",
    "raw_channel_count": "当前测得的通道数"
  }
}
```

保存中间状态有三个目的：

1. **可审计**：可以证明陆地来自厚度阈值，而不是渲染器偷偷画的。
2. **可重画**：不重新模拟，也能更换颜色、字体和排版。
3. **可诊断**：可以检查哪一帧开始减速、沉降、出水和分流。

这也是 V9 与“直接让模型生成一段看起来像三角洲的视频”的核心差别：V9 能追溯
每一个画面元素的数据来源。

## 7. 第四步：自动机制门禁

在正式绘图前，
[`validate_mechanism.py`](../../blackbox/v9_causal/validate_mechanism.py)
重新读取 `states.jsonl`，独立检查机制是否满足约束。它不会只相信模拟器自己打印的
“success”。

正式结果的检查如下：

| 检查                 | 结果      | 意义           |
| ------------------ | ------- | ------------ |
| 状态数在 100–120 范围    | 通过，120  | 时长符合任务限制     |
| 沉积厚度单调增加           | 通过      | 没有凭空减少海床沉积   |
| 新生陆地单调增加           | 通过      | 已出水区域没有无因消失  |
| 陆地严格等于阈值公式         | 通过      | 渲染前的数据没有手画陆地 |
| 到岸后才开始沉降           | 通过      | 因果顺序正确       |
| 出水前至少有 7 帧水下沉积     | 通过      | 不是泥沙一到就立刻变陆地 |
| 河口减速可测             | 通过      | 沉降原因有数值支撑    |
| 最终自发形成 2–3 条通道     | 通过，2 条  | 出现绕流分支       |
| 通道至少稳定 5 帧         | 通过，15 帧 | 不是单帧噪声       |
| 新生陆地是一个连通体         | 通过      | 没有无关的远处孤岛    |
| 出水前缘达到 grid x≥50   | 通过，x=51 | 陆地不只贴在岸边     |
| 水下沉积前缘达到 grid x≥56 | 通过，x=62 | 能看到更远的沉积输运   |
| 正式机制使用生成模型         | 通过，空列表  | 无生成模型参与      |

完整机器可读结果见
[`validation.json`](mechanism/validation.json)。另外还生成了只用于诊断的证据：

* [新生陆地 mask 对比图](mechanism/land-mask-contact-sheet.png)；
* [流场对比图](mechanism/flow-contact-sheet.png)；
* [纯文本陆地/沉积切片](mechanism/land-mask-ascii.txt)。

这些诊断文件不是正式视频的一部分。它们存在的原因是：如果成片看起来不对，可以
先判断“机制数据错了”还是“数据正确但画法让人看不懂”。

四个单元测试也全部通过。测试代码位于
[`tests/`](../../blackbox/v9_causal/tests/)。

## 8. 第五步：把 120 个机制状态编排成 105 张展示帧

机制模拟的目标是完整记录过程；正式视频的目标是让人来得及理解。两者不需要逐帧
一一对应。

[`storyboard.json`](../../blackbox/v9_causal/storyboard.json)
定义了五个教学阶段。每个阶段从属于该阶段的机制状态中均匀选取若干状态，再把该
阶段最后一个状态重复 7 次，给字幕和关键变化留下约 0.58 秒的阅读时间。

| 阶段                  |  机制状态范围 | 展示内容    | 动态帧 + 停留帧 |  成片帧范围 |
| ------------------- | ------: | ------- | --------: | -----: |
| 1. transport        |    0–27 | 河流搬运泥沙  |    14 + 7 |   0–20 |
| 2. decelerate       |   28–49 | 入海后流速下降 |    12 + 7 |  21–39 |
| 3. accumulate       |  50–100 | 泥沙层层堆积  |    25 + 7 |  40–71 |
| 4. threshold_change | 101–107 | 沙洲露出水面  |     7 + 7 |  72–85 |
| 5. reroute          | 108–119 | 河道绕行分流  |    12 + 7 | 86–104 |

选择关系逐帧写在
[`timeline.json`](runs/v6-causal/timeline.json) 中。例如它会明确记录：
“展示帧 21 来自机制状态 28，字幕为入海后流速下降，不是停留帧。”

因此三个数字分别表示不同层级：

* **120 个机制状态**：模拟器记录的完整因果过程；
* **105 张 PNG**：为了教学节奏选出的正式展示帧；
* **GIF 内部 70 个图像记录**：无损优化器合并了相同的停留帧。

GIF 仍然播放 8.75 秒。70 不是丢帧，而是“同一张图保持更长时间”的压缩表达。

## 9. 第六步：Python 如何把状态画成画面

正式渲染由
[`render.py`](../../blackbox/v9_causal/render.py) 完成。它逐帧读取状态，不调用
生成模型。每种数据都有固定视觉映射：

| 状态数据               | 画面表示       | 观众应读出的含义      |
| ------------------ | ---------- | ------------- |
| 原有陆地 mask          | 灰绿色斜线区域    | 动画开始前已经存在的陆地  |
| `flow_samples` 的方向 | 箭头朝向       | 水往哪里流         |
| `flow_samples` 的速度 | 箭头长度和明暗    | 箭越短，水越慢       |
| 悬浮 `particles`     | 赭色小圆点      | 水中正在被搬运的泥沙    |
| `thick`            | 六级半透明赭色沉积层 | 水下泥沙由薄到厚      |
| `new_land`         | 暖绿色区域      | 沉积已经超过水深、露出水面 |
| `new_land` 的边缘     | 亮黄色细边      | 新生陆地正在扩展的边界   |
| 当前 `beat_id`       | 底部中文字幕和进度点 | 当前讲解的因果阶段     |

渲染顺序为：

1. 铺海水底色；
2. 根据原有陆地 mask 画灰绿色陆地和斜线；
3. 根据 `thick` 画水下沉积；
4. 根据 `new_land` 盖上新生陆地；
5. 根据颗粒坐标画悬浮泥沙；
6. 根据 `flow_samples` 画水流箭头；
7. 画固定图例、阶段字幕和进度点。

箭头最后画在颗粒之上，是为了避免泥沙点遮住流速信息。为了防止数百颗粒把画面
塞满，渲染器只显示编号能被 7 整除的颗粒。这个抽样规则固定且可复现；它只降低
画面密度，不修改颗粒路径，也不影响沉积计算。

这里也解释了为什么“Python 动画”可以画出不只是运动轨迹的细节：流场求解器和
沉积模拟器负责产生结构，Pillow 根据结构画出颜色、箭头、纹理、图例和文字。
Python 并不是只控制一个局部动作，也不是逐帧调用 AI 补完背景。

正式帧保存在
[`runs/v6-causal/frames/`](runs/v6-causal/frames/)。

## 10. 第七步：从 PNG 导出 MP4、GIF 和检查材料

[`export.py`](../../blackbox/v9_causal/export.py) 先调用渲染器生成 105 张 PNG，
再生成以下交付物。

### 10.1 MP4

FFmpeg 按文件名顺序读取 `0000.png` 到 `0104.png`，使用：

* 帧率：12 fps；
* 编码器：H.264 / `libx264`；
* 质量：CRF 18；
* 像素格式：`yuv420p`；
* `+faststart`：便于网页或播放器更快开始播放。

输出：
[v6_causal.mp4](runs/v6-causal/v6_causal.mp4)。

### 10.2 GIF

GIF 不是直接把每张 PNG 随便量化，而是经过四步：

1. FFmpeg 浏览全部帧，生成最多 128 色的全局调色板；
2. FFmpeg 使用同一调色板量化所有帧，关闭抖动 `dither=none`；
3. Pillow 重新封装为共享调色板和差分矩形，并用 80/80/90 ms 循环组合得到精确的
   平均 12 fps；
4. gifsicle `-O3` 做无损结构优化。

输出：
[v6_causal.gif](runs/v6-causal/v6_causal.gif)。

关闭抖动是为了避免海水和沉积区域出现无意义的闪烁噪点。共享调色板则保证同一种
状态颜色不会在不同帧间跳变。

### 10.3 Contact sheet、时间线和元数据

* [contact-sheet.jpg](runs/v6-causal/contact-sheet.jpg)：把 8 个关键时刻排在一张图上；
* [timeline.json](runs/v6-causal/timeline.json)：记录每张展示帧来自哪个机制状态；
* [metadata.json](runs/v6-causal/metadata.json)：记录尺寸、时长、编码命令、文件大小、
  SHA-256、媒体探测结果、是否使用 GPU/模型等；
* [palette.png](runs/v6-causal/palette.png)：GIF 使用的全局颜色表。

这就是为什么一个“视频结果”旁边会有很多文件：MP4/GIF 给人看，PNG 是源帧，
JSON 用于追溯，contact sheet 用于快速评审，palette 是 GIF 编码的中间材料。

## 12. 辅助坐标 VLM 为什么失败，为什么不影响主结果

V9 任务允许把坐标 VLM 作为辅助检查，但不允许它代替人工理解测试。本地 Gemma 3
12B 在正式结果完成后读取关键图像，尝试报告海岸线和沉积前缘坐标。

运行条件：

* CUDA/HIP 均隐藏；
* 只使用 CPU；
* 用时 216.781 秒；
* 不生成或修改任何正式画面。

它返回了被截断的 JSON，并将实际约 `304/408 px` 的可见位置误报为 `700/760 px`。
因此状态记录为失败，原始结果保存在
[`coordinate-vlm.json`](reviews/coordinate-vlm.json)。

这个失败反而说明：模型给出的“看起来像理解了”的文本不能作为教学解释力证据。
机制正确性应由状态和自动门禁证明，观众是否理解则应由真实人类盲测证明。

## 13. 九次参数尝试是怎样筛选的

调参目标不是让图形“更像预先想好的三角洲”，而是让同一套因果规则同时满足：

* 泥沙确实先被搬运；
* 到海后可测量地减速；
* 有一段可见的水下沉积过程；
* 沉积能够出水，但不在河口立刻筑成横墙；
* 新生陆地形成后，水流能够自行绕行；
* 分流持续稳定，而不是一帧噪声。

| 尝试 | 单变量变化            | 观察与决定                           |
| -- | ---------------- | ------------------------------- |
| 01 | 默认沉降率 0.28       | 岸边过早形成窄障碍，拒绝                    |
| 02 | 沉降率 0.12         | 沉积稍远，但出水仍集中在岸边，拒绝               |
| 03 | 沉降率 0.05         | 沉积前缘改善，但第一次出水过晚，继续诊断            |
| 04 | 沉降率 0.02         | 颗粒输运到 grid x=57，但 120 帧内没有陆地，拒绝 |
| 05 | 单次沉积质量 0.12      | 能够出水，但等幅速度让开阔海域被误测为流廊，拒绝        |
| 06 | 速度乘以势场梯度强度       | 真正的集中流廊出现，但沉积较斑驳，继续诊断           |
| 07 | 分散半径 1→2         | 沉积连接成整体，但仍有后期封堵风险，继续诊断          |
| 08 | 扩张率 0.72→0.35    | 最后 15 帧稳定两条通道且没有封堵，接受           |
| 09 | 单次沉积质量 0.12→0.18 | 过早形成宽墙，水流远距离绕行，拒绝               |

正式结果使用尝试 08 的参数。尝试 09 是一次反向验证：质量继续增加确实会破坏机制，
因此没有因为它“更新”就覆盖正式结果。

每次尝试的参数、stdout 和诊断材料保存在
[`mechanism/attempts/`](mechanism/attempts/) 和
[`blackbox/v9_causal/logs/`](../../blackbox/v9_causal/logs/)。

## 17. 这次真正解决了什么，仍有什么限制

### 17.1 已解决

* 不再用预先画好的目标多边形插值出三角洲；
* 水流、沉积、新陆地和绕流之间形成了可检查的因果闭环；
* 先显示水下沉积，再显示出水陆地；
* 箭头长度提供了明确的减速线索；
* 每个画面元素都能追溯到状态字段或列入“教学排版元素”；
* 正式结果可在无 GPU、无生成模型的条件下快速复现；
* 机制错误和视觉解释错误可以分开诊断。

### 17.2 尚未解决或不能夸大的部分

* 这是为教学动画设计的简化机制，不是高精度水动力学或地貌学模拟；
* 水深、减速公式、沉降概率和网格尺度是解释性参数，不对应特定真实河流的测量值；
* 当前出水陆地前缘约为 408 px，水下沉积前缘约为 496 px，不能把后者误称为陆地；
* 颗粒显示经过固定抽样，画面中的点数不等于模拟中的全部颗粒数；
* 两条通道是这次参数和种子下的涌现结果，不代表所有参数都会形成两条；
* 坐标 VLM 评测失败；
* 最关键的三人零基础盲测仍未完成，所以教学解释力尚不能宣称正式通过。

## 18. 对 V9 三个验收问题的直接回答

### 18.1 人工盲测是否通过？

**尚未通过，因为正式三人盲测还没有执行。** 当前只有机制门禁通过和项目参与者的
主观正面反馈，二者都不能替代盲测。

### 18.2 哪些视觉编码在盲测中失效，为什么？

**目前没有真实盲测数据，不能编造失效结论。** V9 已针对 V8 的主要问题做了如下
修改：静态色块改为运动颗粒和分层沉积；缺少速度信息改为箭头长度编码；陆地直接
出现改为先显示水下沉积再跨越阈值；无引导改为固定图例和五段字幕。它们是否足够
有效，仍要由三位零基础参与者回答。

### 18.3 哪些 primitive 可以复用？

以下机制模块可以独立复用：

* `flow_field`：在障碍物变化后重新计算流向；
* `transport`：沿流场搬运颗粒；
* `decelerate`：把空间扩张映射为速度下降；
* `accumulate`：把离散落点累积为连续厚度；
* `threshold_change`：把连续量跨阈值转为新状态；
* `reroute`：让新障碍反馈到下一帧流场。

它们不依赖目标三角洲轮廓，也不写死分流数量。更详细的复用契约见
[`primitives.md`](primitives.md)。

## 19. 结论

V9 的正式 GIF/MP4 不是由视频模型生成的一段“像三角洲”的画面，而是由一套可复现
的简化因果机制逐帧计算，再由 Python 把状态翻译为教学视觉，最后由媒体编码工具
封装而成。

目前可以可靠声称的是：

> 机制数据通过了自动检查；泥沙搬运、减速、沉积、出水和绕流在状态层面形成了
> 连续因果链；正式成片与状态之间可逐帧追溯。

目前还不能声称的是：

> 零基础观众已经被证明能够只看一次就理解全过程。

下一步不是继续盲目调参数，而是完成三位零基础参与者的正式盲测。若有人答错，应先
根据其原话判断是“机制缺失”还是“视觉编码不清”，再决定修改模拟规则、画面映射、
字幕节奏或图例。
